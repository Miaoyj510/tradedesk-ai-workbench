## 二、违约项（按严重度）

### P1-1 · 结构化通道绕过买家国别与 HS 过滤

| | |
| --- | --- |
| 条款 | 清单 1.8、FR-KB-05、FR-GRC-05「按『买家所在国 + 当前日期』过滤」 |
| 位置 | `src/tradedesk/retrieval/pipeline.py:300`（`structured = _structured_hits(self.chunks, query)`）、`:165-195` |

`_structured_hits` 拿的是**全集**，而且只做时效过滤 —— 国别、HS 编码、文档类型一概不过。
结构化通道本意是"型号/证书号/条款号精确匹配"，但它匹配什么就返回什么，
**不管这个块适不适配当前买家**。复现（BR 买家）：

```
GET /kb/search?q=REG-AE-099...&country=BR
-> 命中 ['REG-AE-099', 'REG-BR-077']      ← 阿联酋条款返回给了巴西买家
```

草稿侧侥幸没出问题（`_citations_from_hits` 里有国别过滤），
但**检索层与 `/kb/search` 接口是敞开的** —— 审核条款 1.8 的口径是"检索时按国别过滤"，
不是"引用时过滤"。

最小改法：结构化通道先过 `filter_by_attributes`（至少国别 + HS + doc_type），
只对"型号/标识精确命中"这一项放宽其余条件。

### P1-2 · 属性过滤把结果清空时，静默回退到全集

| | |
| --- | --- |
| 条款 | FR-KB-05（同上）、PRD 9.4 难点② |
| 位置 | `src/tradedesk/retrieval/pipeline.py:298`（`scope = kept if kept else self.chunks`） |

这行的语义是"过滤后还剩东西就用剩下的，一个不剩就用全集"。
于是**当过滤条件把所有块都滤掉时，过滤条件本身被整体丢弃**：

```
买家 BR + HS 编码 9999.99（库里不存在）
-> 命中 ['M-77', 'TERM-LEADTIME', 'TERM-MOQ']    ← HS 不匹配的 M-77 被放行
```

过滤出 0 条的正确处理是**返回空 + 转人工追问**，不是"那就不滤了"。

最小改法：去掉这个兜底；`kept` 为空就直接返回空结果。

### P1-3 · 买家国别未知时，别国法规条款混进同一封报价

| | |
| --- | --- |
| 条款 | FR-KB-05、FR-GRC-05；清单 §三.4「未生效条款是否被当成当前要求输出」的同类问题 |
| 位置 | `src/tradedesk/agents/inquiry.py:289` |

引用装配的国别判断是 `if country and c.countries and country not in [...]` ——
**国别为空时整个条件短路，等于不过滤**。实测国别未知的询盘，引用里同时出现：

```
引用 = [X-200, CERT-CE-2041, REG-EG-045(埃及), REG-EU-112(欧盟), REG-BR-077(巴西), TERM-LEADTIME]
```

一封报价同时向买家承诺欧盟、埃及、巴西三国的合规要求 —— 这是**对外内容失真**，
而且是买家一眼能看出的那种。

最小改法：国别未知 → 不引用任何**国别专属**条款（只留通用条款与产品/证书），
并把线程标为需人工确认（先问目的港所在国）。

### P1-4 · 检索没确认产品时，回退到 S1 写死常量报价格

| | |
| --- | --- |
| 条款 | 清单 1.9「草稿数据来自知识库，不是写死常量」、FR-KB-07（引用可回指） |
| 位置 | `src/tradedesk/agents/inquiry.py:193-205`（`else: products = self._match_products(message)`）、`:139-153` |

S3 提交说明自己写了这条口径：

> 产品必须被结构化通道确认才可进草稿，否则宁可追问也不猜型号与价格。

**代码没做到。** 买家没点名型号、只说了品类词时：

```
message: "Send me your best price for the manual hydraulic hand truck."
-> status=draft_ready
   正文: "Thank you for your enquiry about X-200. Our reference price for 1000 pcs is USD 4.85–5.2..."
   引用: ['SKU X-200 v1', 'CERT-CE-2041']
```

两个后果：

1. **价格有两个真源** —— 知识库块（`kb_seed.py`）与 S1 的 `data/seed.py::demo_products`。
   库里改了价，走兜底路径的草稿还是旧价（见 P1-5）。
2. **引用断链** —— `SKU X-200 v1` 是 S1 时代的引用格式，知识库里查不到，
   FR-KB-07「每条检索结果必须携带可回指标识」不成立（审核断言 5.4 实测命中）。

最小改法：检索器不可用或未确认产品 → 走"信息不足只发追问"那条路径，
**删掉 `_match_products` 兜底**；`data/seed.py` 的 `demo_products` 降级为纯单测夹具。

### P1-5 · 改库后同一进程内不生效（缓存不失效）

| | |
| --- | --- |
| 条款 | 清单 1.9「改库里的价格 → 草稿价格随之变化」 |
| 位置 | `src/tradedesk/retrieval/store_retriever.py:21-27` |

```python
if self._cache_key != key or len(chunks) != len(self._cache):
```

缓存键是 `(kb_version,)`，失效条件是**块数变了**。改内容不改块数 → 缓存不刷新：

```
改库（price_low 12.3 → 9.99，块数不变）
同一进程内新草稿: "USD 12.3–13.1"     ← 旧价
新进程新草稿:     "USD 9.99–13.1"     ← 新价
```

`verify_s3.py` 场景 8 每次都 `create_app` 重建，所以这条测不出来。
真实形态是长驻进程 —— **知识库改了，检索层不认**。

最小改法：缓存键带上库里块的版本号/最大 `updated_at`；
16 块的规模其实**根本不需要缓存**，直接每次读库最省事。

### P2-1 · 工厂体系证书被表述成"型号由该证书覆盖"

| | |
| --- | --- |
| 条款 | FR-GRC-05、PRD 引用正确率 100%；清单 §三.2「引用与草稿正文是否一致」 |
| 位置 | `src/tradedesk/agents/inquiry.py:246` + `CERT_LINE` 模板 |

模板写死了 "The model is covered by certificate {cert_no}"。
`CERT-ISO-9001` 是**工厂质量体系证书**（`covers=[]`，即未声明覆盖任何型号），
但 BR 买家的草稿正文里出现了：

> "The model is covered by certificate CERT-ISO-9001 (ISO 9001), valid until 2027-01-15."

对买家做的**合规声明失真**（ISO 9001 证的是工厂体系，不是型号）。

最小改法：证书行按 `cert_type` 选模板（产品认证 / 体系证书 / 检测报告），
或只引用 `covers` 明确包含该型号的证书。

### P2-2 · 产品属性数值写进了正文文本块

| | |
| --- | --- |
| 条款 | PRD 9.3 分块策略明文：「产品属性不进文本块，走属性过滤」；PRD 9.4 难点③ |
| 位置 | `src/tradedesk/data/kb_seed.py:27-37` 等三处产品块 |

PRD 9.3 的分块策略写得很清楚，PRD 9.4 难点③ 还给了理由：

> 规格参数（厚度、承重、MOQ）—— 语义检索可能给出"约等于"的数值 → 走属性过滤，数值不经过 LLM 生成

实现把 "MOQ 1000 台，交期 25-30 天，参考价 USD 4.85-5.20 每台" 全写进了正文，
数值又在 `extra` 里存了一份。**现在词法通道无所谓，S4 接上向量通道后这些数字就会进语义通道** ——
正是 PRD 要防的那件事。**S4 开工前必须先改数据建模，否则向量通道一接上就带病运行。**

最小改法：产品块正文只留描述性文字（材质、用途、适用场景），数值全部只留在 `extra`。

### P2-3 · 同一产品没有 4 语版本分别入库

| | |
| --- | --- |
| 条款 | FR-KB-01「同一产品 4 语版本均可入库并被正确召回」；PRD 9.1「中文资料与三种买家语种下各存一份」 |
| 位置 | `src/tradedesk/data/kb_seed.py`（每个 SKU 一个块，`lang="zh"`，四语正文拼在一起） |

现状：每个产品只有 1 个块，四种语言挤在同一段正文里。
后果不只是"没按 PRD 分块"，还有两个具体的：

- 命中原因会说"语言是 zh"——**语种维度的评测（PRD 8.7 L-3/L-4 按语种分层）没法做**；
- 词法通道靠字符 bigram 硬扛跨语（S3 已声明 L2「多语种知识块正文四语并列，词法区分度有限」）——
  分成 4 个块之后区分度立刻不一样，且为 S4 的语种分层评测留了接口。

最小改法：按语言拆块（每个 SKU 4 个块，`lang` 各自标注 + `aliases` 挂多语别名）。

### P2-4 · `/kb/search` 把买家国别无关的合规条款对外暴露

与 P1-1 同根因，单列是因为它是**对外接口**：`GET /kb/search?country=BR` 返回了 `REG-AE-099`。
接口文档/前端一旦接上，这个洞就在业务侧可见。修 P1-1 时一并解决。

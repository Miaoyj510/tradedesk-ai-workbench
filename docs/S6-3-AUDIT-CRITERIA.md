## 一、发布单元与版本化（PRD 13.4.8「发布单元」）

| # | 判据 | 怎么验 |
| --- | --- | --- |
| U1 | 四类发布单元**各自有版本号**：① 镜像（应用）② AgentSpec / Prompt ③ 术语表 / 知识库索引 ④ 名单库 | 每类都能报出版本 |
| U2 | 四类**可独立回滚**（回滚其中一类不动其他三类） | 独立回滚后各单元版本号符合预期 |
| U3 | Prompt / AgentSpec / 术语表 / 名单库 / 索引 的版本是**数据**，不是代码里的常量 | 换版本不改代码即可生效 |
| U4 | 索引回滚**不重建**（PRD 明写"索引用双索引 + 别名切换，避免重建窗口"） | 回滚后旧索引仍在、无重建调用；且**重建期间旧索引仍可用** |

> U4 是 PRD 13.4.8 与风险 R-14 的硬要求，也是本项目**已有**的坑的重灾区
> （R15-02「重灌种子连带删掉向量索引」、R17-03「进程内索引是启动快照」）。

## 二、灰度（PRD 13.4.8「灰度维度」「灰度比例」）

| # | 判据 | 怎么验 |
| --- | --- | --- |
| G1 | 灰度**按企业**分流：同一企业内部所有买家拿到**同一版本** | 多买家同企业 → 版本一致 |
| G2 | 同一买家在不同时间点（多次询盘）拿到**同一版本**（不能每次重新分桶） | 同一 buyer_id 重复询盘 → 版本稳定 |
| G3 | 分桶**确定性**（同样的输入 → 同样的结果，可复现、可审计） | 同输入两次分桶结果一致 |
| G4 | 比例档位：**1 家试点 → 20% → 50% → 100%** | 档位枚举存在且顺序正确 |
| G5 | 每档有**观察期**（PRD：每档观察 ≥ 1 个工作日），未到观察期不得晋级 | 晋级被拒 |
| G6 | 可按**语种**单独灰度 | 语种维度存在且生效 |

> G1/G2 是 PRD 明写的理由："避免同一买家被不同版本应答"。
> G3 是灰度的前提：不可复现的分桶等于没有留痕依据。

## 三、回滚（PRD 13.4.8「回滚」）

| # | 判据 | 怎么验 |
| --- | --- | --- |
| B1 | **一键回滚**覆盖三类：镜像回滚 + Prompt/AgentSpec 版本回滚 + 索引版本回滚 | 一次操作三类都回到目标版本 |
| B2 | 回滚**不丢数据**（不 truncate 业务数据与审计日志） | 回滚前后业务表行数与审计日志条数不减 |
| B3 | 回滚**有留痕**（谁、何时、从哪个版本到哪个版本、为什么） | 回滚事件可查 |

> B2 是本项目的**既有坑**：R15-03「建索引脚本会清空业务数据与审计日志（`store.reset()`）」。
> 回滚脚本走 `store.reset()` 就会重犯。

## 四、变更冻结与发布审计（PRD 13.4.8「变更冻结」「审计」）

| # | 判据 | 怎么验 |
| --- | --- | --- |
| C1 | 法规库 / 名单库更新走**独立发布流程**，与普通发布**分开** | 名单库发布有独立路径与独立标记 |
| C2 | 名单库/法规库更新**必须重跑 L-6 风险用例集**（召回 ≥99%、误报率）后才能放量 | 未跑 L-6 → 放量被拒 |
| C3 | 每次发布记录**5 要素**：版本号、变更内容、审批人、灰度范围、回滚预案 | 缺任一 → 记录不完整（要能查出来） |

> C2 的依据是 PRD 13.4.8 明文 + 8.7 的 L-6 定义；L-6 = 名单与法规用例集，
> 语种无关，指标是召回 ≥99% 与误报率。
> C3 的 5 要素是 PRD 逐字列的，**少一项都不算留痕**。

## 七、断言怎么写（审核方承诺）

- **不复用**实现方的自证脚本（`verify_s6.py` / `verify_s6_ui.js`）——R21 的教训：
  自证只测了它自己测的那层。
- **双后端跑**（SQLite + PostgreSQL）：发布/回滚涉及存储，跨后端不一致是本项目的老坑（R17-01）。
- **断言写行为，不写实现**：测"同企业买家同版本""回滚后旧索引仍在"这类**可观察行为**，
  不测"某个函数叫什么名字"。
- **口径类断言必须有**：见 §零。

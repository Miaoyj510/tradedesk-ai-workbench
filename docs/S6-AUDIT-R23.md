- **BFF 式的读模型与"业务规则全在后端"**：灰度分流不重算闸门、不重算引用，

## 二、5 个根因

### R23-01 · 「双索引 + 别名切换」只做了台账，**底层不可能共存** → 回滚必然重建（P1，口径失真 + 功能缺失）

**PRD 13.4.8 的回滚行明写**：

> 回滚 | 镜像回滚 + Prompt/AgentSpec 版本回滚 + **索引版本回滚**（**索引用双索引 + 别名切换，避免重建窗口**）

**验收基线 `docs/S6-ACCEPTANCE.md` 的 G9 也这么宣称**：

> G9 | PRD 13.4.8 | 回滚索引采用**双索引 + 别名切换**：建新版本**不切 active**，回滚后新旧块与向量都还在

**实现方修复记录的「口径提醒」也这么宣称**：

> 本期做到的是"本地机制可验证"（分桶、观察窗、分类别回滚、**双索引别名切换**、越权闸门）

**实测：不成立。**

审核方探针（`audit_s6_release.py` §S6-H「G9 双索引」）：

```
建 A 后：向量 28 / 块 28
建 B 后：A 的向量剩 0、A 的块剩 0、B 的向量 28     ← 覆盖式重建
```

**根因在存储层**（`store/sqlite_store.py` / `postgres_store.py`）：

```sql
CREATE TABLE kb_embeddings (
    chunk_id   TEXT PRIMARY KEY,     -- ← 单列主键
    kb_version TEXT NOT NULL DEFAULT '',
    ...
);
```

```python
def upsert_kb_embedding(self, chunk_id, kb_version, model, vector, content_fp=""):
    ... "INSERT INTO kb_embeddings(...) VALUES(...) ON CONFLICT(chunk_id) DO UPDATE SET
         kb_version=excluded.kb_version, ..."
```

→ **同名 chunk_id 只能存一份向量**；灌新版本 = 旧版本被顶掉。
块侧同理：`load_kb()` 是 replace 式（灌 B 后 `list_kb_chunks("kb-A")` = 0）。

**为什么自证脚本没发现**：实现方的 `verify_s6_3.py` 第 6 节「双索引」是这么构造的 ——
**在测试 fixture 里手工给 chunk_id 加版本后缀**：

```python
v2_chunks = build_demo_chunks(KB_V2)
for c in v2_chunks:
    c.chunk_id = c.chunk_id + "-v2"      # ← 只有测试脚手架这么做
```

于是"v1 与 v2 块共存"这条断言是绿的 —— 但它证明的是
「**如果有人手工加后缀就能共存**」，而**生产路径（`load_kb` / `index_kb`）根本不加后缀**。
他们的注释其实已经写明了："kb_chunks 的主键是**单列 chunk_id**，同名会直接覆盖 v1"。

**连"诚实边界"里那句也不成立**：

> 知识库块表主键仍是**单列 `chunk_id`**：两版本共存靠**版本后缀区分**，生产化应改为 `(chunk_id, kb_version)` 复合主键

—— "版本后缀区分"**只存在于测试 fixture**，生产路径没有。

**修法**（两处，缺一不可）：
1. **存储层**：`kb_chunks` / `kb_embeddings` 主键改 `(chunk_id, kb_version)` 复合主键
   （SQLite 与 PostgreSQL 都要；PG 侧还要重建 HNSW 索引并考虑按版本的部分索引）；
   `content_fp` 失效键（R15-01）也要带版本维度。
2. **灌种子改成按版本 upsert**，不删别的版本；启动时的重灌只在"**一个版本都没有**"时做，
   而不是"基线版本为空就灌"（见 R23-02）。
   → 或者：把 `index_version` 组件删掉，并在验收基线里**明确写"索引版本回滚属生产化项"**
   （那也是合规的答案 —— 不许沉默）。

### R23-02 · 灰度用的库版本**在进程重启后必然被抹掉**（P1，功能失效且静默）

**根因**：`api/deps.py:78-80` 启动时的重灌逻辑

```python
existing = self.store.list_kb_chunks(self.kb_version)
if not existing:
    load_kb(self.store, self.kb_version)      # ← replace 式：把别的版本全抹掉
```

因为 `load_kb` 是 replace 式，而上一版（灰度版）的块把基线顶掉了 → 启动时基线为空 →
**重灌基线 → 灰度版的块被抹掉**。

**实测**（审核断言「灰度库版本必须能跨进程重启存活」）：

```
灌灰度版后 28 块；模拟重启（新建 AppContext）后剩 0 块
（启动时重灌基线把灰度版抹掉了 → knowledge 类别的灰度重启后必然失效）
```

**为什么这是 P1**：`knowledge` 类别的灰度发布，**在进程重启后就没了** ——
而发布台账仍显示该企业在灰度里、审计链完整、事件流里有 `release.assign`。
业务员看到的是"AI 突然不报价了"，而**没有任何地方说它为什么**。

**而且触发它的是日常运维动作**：`scripts/index_kb.py:68` 调 `load_kb(store, cfg.kb_version)`
→ 运维跑一次 `dev.ps1 index`（**显式的、日常的、还会计费的**动作），
**灰度版本的块与向量当场被清空**。这正是 PRD 13.4.8 禁止项那条
"不允许在**无灰度**的情况下批量重灌向量索引"没有护栏的地方。

> 顺带说明：他们的注释写"load_kb 是幂等重灌种子，且不删向量（R15-02）" ——
> **对同一个版本**成立（R15-02 修的就是这个），但**对别的版本**，
> 它既删块也删向量。多版本场景没被考虑。

**修法**：与 R23-01 的第 2 点同源（灌种子按版本 upsert + 启动只在空库时灌）；
另外 `index_kb.py` 不应无条件重灌基线（至少要"该版本已存在则跳过"）。

### R23-03 · 灰度到一个**未就绪**的库版本不被拦 → 灰度企业静默退化成"请补充信息"（P1，对外失真）

**事实**：`release/service.py` 的 `resolve()` 只比对版本**字符串**，
不检查该版本在库里**有没有块、有没有向量**；`create()` 也不校验。

**实测**（审核断言「灰度到一个未就绪的库版本 → 必须被拒或被分流拦下」）：

分流到 `kb-2026.99-z`（库里根本没这个版本）之后：

| | 草稿 |
| --- | --- |
| **灰度企业**（CANARY CO） | `Hi, To quote accurately, could you confirm the model / SKU, the quantity, the destination port and your preferred Incoterm?` —— **无价格** |
| **稳定企业**（Other Ltd） | `Thank you for your enquiry about X-200. Our reference price for 1000 pcs is USD 4.85–5.2 per unit FOB Shenzhen, with a lead time of 25–30 days...` |

→ **同一个产品、同一条询盘，灰度企业拿不到报价，稳定企业拿得到。**
而发布台账一切正常、审计链完整、事件流里有 `release.assign`。

**为什么这是 P1**：本项目的核心卖点是"引用可回指 + 数值唯一真源 + 不猜测"。
降级本身是**安全侧**的（宁可不给价也不给错价，这点做对了），
但它是**静默的功能失效** —— 没有任何告警说"这个灰度版本没有知识库"。

**修法**：`create()` 与 `resolve()` 都要校验目标 `kb_version` 在库里**可用**
（块数 > 0；走稠密通道的话还要有向量），不可用就**拒绝发布 / 拒绝分流**（fail-fast > 静默降级）；
灰度台账里显式标出"该版本不可用"。

### R23-04 · `index_version` 是**装饰性组件**（P2，改了它不会有任何效果）

**事实**：清单里新增了 `index_version`（归 knowledge 类），
但**没有任何模块消费它** —— 检索路径只认 `kb_version`：

```
api/deps.py 的 _retriever_factory(kb_version) → load_index(self.store, key)
```

审核断言「index_version 必须被检索/回滚路径消费」实测：
`deps.py` / `workbench.py` / `indexer.py` / `store_retriever.py` / `supervisor.py` /
`inquiry.py` / 三个 store 文件里**没有一个出现 `index_version`**；
只有 `release/` 模块与自证脚本在**写**它。

**为什么有影响**：实现方的修复记录说"要单独把索引指向另一套**已建好**的索引，
显式给 `index_version` 即可 —— 别名切换，不重建"。
**这句话现在是不成立的**：显式给 `index_version` 什么都不会发生。

这正是本项目的老形态（R17 / S15-03 记过）：
**"标志位只有声明没有守卫，等于装饰"**。

**修法**：要么让检索/回滚真的按 `index_version` 取索引（配合 R23-01 的复合主键），
要么**把这个组件删掉**并在验收基线里写明"本期 knowledge 类回滚 = 块 + 索引一起切"。

### R23-05 · 回归 / L-6 证据是**任意非空字符串**（P2，PRD 禁止项形同虚设）

**PRD 13.4.8 禁止项**：

> 不允许**跳过回归直接改 Prompt**

**实现**：只校验"证据字段非空"。审核断言实测：填一句
`"随便写点什么"` 就能建出一次改了提示词的灰度发布。

**为什么有影响**：与首轮的"审批人可伪造"同族 —— **自称即通过**。
禁止项要成立，证据得**可核验**（比如：要求填回归报告号，且该报告号能在回归台账里查到；
或要求贴报告文件路径并校验其存在）。

**修法**：证据字段改成**引用**（报告编号 / 报告文件），建发布时校验其可解析到已登记的回归产物；
名单库变更的 L-6 证据尤其要绑到具体的风险用例集运行记录上。

## 三、修复顺序建议

| 顺序 | 根因 | 优先级 | 一句话 |

## 五、这一轮的方法论（值得记）

1. **判据与脚本都写于实现交付之前**（`docs/S6-3-AUDIT-CRITERIA.md` 22 条 + 41 项断言）。
   否则审出来的东西会被实现反向塑形 —— 审的就不是 PRD 13.4.8，是实现自己。
2. **断言写行为，不写实现**：G9 那条不查"有没有叫 index 的组件"，而是
   **实测"建新版本后旧版本的块与向量还在不在"**。
   正因为这样，才抓到了"自证脚本用手工 fixture 证明了一个生产路径不存在的行为"。
3. **审核方自己的脚本也会有假阳性与空断言**，必须逐条核实：本轮修掉了 4 处
   （正则过宽、中文数字、灰度时序、空集合蒙混过关）。**审核方出假阳性比漏报更伤公信力**。
4. **在制品上先试跑**：实现方还在改的时候先跑一遍，把"已修好"和"交付时就有问题"分开，
   不把在制品的中间态算成缺陷。

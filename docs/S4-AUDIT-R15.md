  而且直接约束了 4b 的设计（结构化通道才是型号识别的唯一权威）。

**问题出在三个地方**：向量的**失效键**、**计费路径**、**口径声明**。

## 二、违约项

### R15-01 · 向量的失效键只有"模型标签"，不含块内容（P1，与 R11-07 同类）

| | |
| --- | --- |
| 条款 | 验收 4a-04「索引流程幂等」、PRD 9.3 引用装配与库版本留痕；S3 的同类问题 R11-07 已用**内容指纹**修过 |
| 位置 | `src/tradedesk/retrieval/indexer.py:32-47`（`embedder_tag` / `index_kb` 的 todo 判定） |

失效键是 `name/model/dim`，**不含块内容**。于是：块正文改了、库版本号没升 → 块被判定为
"已索引过" → **向量不重算** → 向量通道返回旧内容：

```
改块正文（版本号不变）→ 再次 index_kb → indexed=0，向量与改之前逐位相同
```

这正是 R11-07（"改库后同进程内不生效"）在向量层的翻版。S3 那次的解法是**内容指纹**，
这里照抄即可。

最小改法：失效键带上块内容指纹（或强制"内容变了必须升 `kb_version`"，并在索引时校验）。

### R15-02 · 重灌知识库种子会连带删掉向量索引 → 建索引脚本每次全量重嵌（P2，白花钱）

| | |
| --- | --- |
| 条款 | 验收 4a-04「同一模型版本不重复嵌入」、PRD 成本硬指标「单位询盘 Token 成本 ≤ 0.2 元/条」 |
| 位置 | `src/tradedesk/store/{sqlite,postgres}_store.py::clear_kb`（同时 `DELETE FROM kb_embeddings`）+ `scripts/index_kb.py:67`（无条件 `load_kb`） |

`load_kb` 是**幂等重灌种子**，`replace=True` 时走 `clear_kb()` —— 而 `clear_kb` 现在
**连向量表一起删**。实测：

```
重灌前 29 条向量 → load_kb(store, KB_VERSION) → 重灌后 0 条
```

索引脚本的顺序是「先 `load_kb`（删光向量）→ 再算 `todo`」→ `existing` 永远是空的
→ **每次运行都全量重嵌**。库函数 `index_kb()` 本身确实幂等（我实测 `indexed=0`），
但**真实使用路径不成立**，验收条款 4a-04 在 CLI 上是假的。

最小改法：`load_kb` 不删向量（向量与块一一对应，块没变就不该删）；
`clear_kb` 拆成"清块"与"清块+清向量"两个语义。

### R15-03 · 建索引脚本会清空业务数据与审计日志（P2）

| | |
| --- | --- |
| 条款 | PRD 11.4「审计日志不可篡改且**全量留痕**」、NFR-SEC-03；不可替换的产品不变量④ |
| 位置 | `scripts/index_kb.py:65-66`（`store.reset()`） |

SQLite 路径下脚本调了 `store.reset()`，它清的是
`threads / customers / thread_events / **audit_log** / gate_tokens` —— 与"建向量索引"毫无关系。
建向量索引要动的是**向量表**，业务表与审计链不该被一个索引脚本顺手抹掉。

最小改法：脚本不碰业务表（向量表本来就独立）。

### R15-04 · 维度变更后留下"有行但向量为空"的残骸，稠密通道会静默失效（P2）

| | |
| --- | --- |
| 条款 | 验收 4a-06「维度不符应被存储层拦下」、PRD 9.5 两层口径（不得宣称做不到的能力） |
| 位置 | `src/tradedesk/store/postgres_store.py::_init_embedding_table`（`DROP COLUMN` + `ADD COLUMN`） |

PG 实测：`vector(4)` → 改成 `vector(8)` → 存储层初始化时自动重建列 →
**行还在，向量列是空的**：

```
换维度后剩 1 行，其中空向量 1 条 ['KB-T-1']
```

`list_kb_embeddings` 把空向量当成一条记录返回 → `load_index` 得到"1 条向量" →
`AppContext` 打印「向量索引已加载：1 条」→ **实际上每条相似度都是 0**。
4b 接入后这会表现为「语义召回没结果」，很容易被误判成"模型不行"，
而不是"索引其实是空的"。

另外两处体验问题：重建列发生在**存储层初始化**（每次启动都可能触发，不是显式动作）；
`AppContext` 只在索引非空时打印提示，索引"非空但全空"时完全静默。

最小改法：重建列后把整表行清干净（或连行一起删）；读回时跳过空向量；
索引"有行但无有效向量"时要显式告警。

### R15-05 · 占位嵌入器不归一、维度随批次变 → "余弦相似度"能算出 9.0（P3）

| | |
| --- | --- |
| 条款 | 验收 4a-05「余弦 TopK」、PRD 9.3 |
| 位置 | `src/tradedesk/retrieval/embedders.py::NullEmbedder.embed`、`src/tradedesk/retrieval/vector_index.py::search` |

`VectorIndex` 假定向量已归一（`cosine` 只是点积），但不校验：

```
未归一向量 [3,0,0] 与自身 → 相似度 9.0（余弦不可能 > 1）
```

而 `NullEmbedder` **既不归一、词表还随批次变化**：

```
NullEmbedder().embed(["hello"])          → 3 维
NullEmbedder().embed(["hello","world"])  → 6 维
```

后果：4b 若在没有云端 key 时用占位嵌入器接线（这是最可能的选择），
dense 通道的分数看起来很正常甚至很高（0/1 向量的点积可以到几十），
会被误当成语义能力；维度不一致时 `cosine` 直接返回 0 → 静默无结果。

最小改法：`NullEmbedder` 固定维度并归一；`VectorIndex` 载入时校验归一（未归一就归一或报错）。

### R15-06 · 查询侧嵌入既不在协议里、也不校验维度（P2）

| | |
| --- | --- |
| 条款 | PRD 13.4.5 选型轴③（可替换实现，接口不变）、验收 4a-02「维度校验」 |
| 位置 | `src/tradedesk/retrieval/base.py::Embedder`、`src/tradedesk/retrieval/embedders.py::embed_query` |

协议里只有 `embed()`，**没有 `embed_query()`** —— 而 4b 的稠密通道要的正是查询侧嵌入。
两个实现都实现了 `embed_query` 纯属巧合，换个实现就断。

更实际的问题是**查询侧不校验维度**：文档侧维度不符会报错（`embed` 里查了），
查询侧不查 → 查询向量维度错了不报错，只是跟所有向量点积为 0 → 静默"召回不到"。

最小改法：协议补 `embed_query`；查询侧与文档侧同口径校验维度。

### R15-07 · 口径声明与实际不一致（四处，P2 —— S3 栽过的同一个坑）

| | |
| --- | --- |
| 条款 | S3 验收清单 §0 口径声明的纪律；PRD 9.5 两层口径 |
| 位置 | `docs/S4-ACCEPTANCE.md`（§0 / §二 / §五 L1 / L6）、`.env.example` |

S3 在"库版本号两份""引用断链"上栽过，**文档口径失真要当缺陷，不能当笔误**。本轮四处：

| # | 文档写的 | 实际 |
| --- | --- | --- |
| 1 | §二 模型口径表：「MiniMax `embo-01`（云端 API，**1024 维**）」；L6：「向量列维度固定（`vector(1024)`）」 | 配置与实测都是 **1536 维** |
| 2 | §0：「本轮的云端嵌入用假 transport 测（不联网、不计费），**真实调用在 4b 手动跑**」；§五 L1：「本轮**没有真实云端嵌入调用**」 | §三 给出的是**真实 key 实测**矩阵 |
| 3 | §0 口径声明只说"不能宣称语义召回能力" | 没写**跨语种对齐弱**（实测 zh↔es/ar ≈ -0.02）—— 4b 极易据此宣称"多语种语义召回" |
| 4 | `.env.example`：「开启后**启动会建向量索引**（会计费）」 | 启动改成**只读**索引，建索引是显式动作 |

最小改法：改这四处；§0 补一句"**当前嵌入模型不提供跨语种对齐，跨语种召回只能靠术语表 + 四语分块**"。

## 三、记账项（不违约，但要记）

| # | 事项 | 说明 |
| --- | --- | --- |
| N1 | `semantic` 标志位**无人消费** | 全项目没有一处读 `.semantic`。标志位立了规矩却没装守卫 —— 4b 接通道时必须显式检查，否则假嵌入器会被当成语义通道用 |
| N2 | HTTP 401/403 会被当作网络错误重试 | `HTTPError ⊂ URLError` → OpenAI 兼容形态的 401 也会重试 2 次（实测 3 次调用）。MiniMax 形态不受影响（错误在 200 的 body 里） |
| N3 | 「产品规格」块的模板句进了向量索引 | 三个 SKU 的文本是同一句模板（"X-200 的规格以结构化属性存放：…"），语义上无信息量。建议 4b 把它们排除在语义通道之外（它们只该走属性过滤） |
| N4 | 维度变更在**存储层初始化**时自动重建列 | 派生数据可重建，但这是启动副作用而不是显式动作；建议改成显式迁移（`dev.ps1 index --rebuild`） |
| N5 | `type=db/query` 是否真的生效，4b 必须验 | 如果云端忽略 `type`，查询向量与文档向量不在同一空间 → dense 通道静默变差。验证办法：同一句话分别以 `type=db` 与 `type=query` 调用，比两个向量的相似度 |
| N6 | 每条询盘 = 1 次查询嵌入（计费） | 成本硬指标 ≤0.2 元/条要在 S5 计量时算进去；4b 上线后每次检索都会调云端 |
| N7 | **没有 ANN 索引** | 4a 的"索引"是把块向量化并落库，不是 pgvector 的近似检索索引（HNSW/IVFFlat）。4b 下推到 pgvector 时要建 HNSW，否则 50–100 并发下线性扫描会成瓶颈 |
| N8 | 换回 BGE-M3 的对照评测 | PRD FR-KB-03 的默认模型是 BGE-M3（多语种强），现在用 embo-01。PRD 12.5 要给硬指标数字 → 4c 评测必须把 BGE-M3 作为对照，否则"跨语种召回率"这个数只能说明 embo-01 的表现 |

## 七、给实现 agent 的一句话

4a 的设计我基本认同：**接口留好、`semantic` 立规矩、索引做成显式动作、默认不计费、
用真 key 实测并把实测结论写进文档** —— 尤其是那三条实测（1536 维、跨语种 -0.02、
向量分不清型号），它们比任何摸测都值钱，直接决定了 4b 的设计。

**但"实测"之后，口径没有跟着改**（文档还写着 1024 维、还写着"没有真实调用"），
**索引的失效键没有跟着内容走**（改了块不重算），**建索引脚本顺手把向量索引和审计日志都清了**
（幂等与留痕两条都破了）。这四条合起来的意思是：
**这条路径现在还不能放心用来建真实索引** —— 一跑就全量重嵌（花钱），一改内容就拿到旧向量。

4b 之前把 R15-01/02/03/06/07 收掉，再把 R14 那三个引用装配的洞补上，就可以放心接线了。

# 作品集页（面试 / 评审用的一页纸）

> 一句话：**给中小外贸团队的"AI 数字员工工作台"** —— 把询盘应答、客户背调、商品运营、投放推广、交易风控拆给五个 Agent，

## 一、三个关键判断（这个项目最值钱的部分）

**判断一：AI 该做"草稿"，不该做"决定"。**
询盘可以自动应答，但**报价必须人工签核、合同必须人工确认**——所以整条链路上写操作与发送是分离的：
Agent 产出草稿 → 11 条闸门评估 → 人签核 → 闸门令牌一次性消费 → 才发出去。
这不是"负责任的措辞"，是代码结构：所有写接口都要求闸门令牌，令牌绑定动作且一次性。

**判断二：这个领域最难的不是模型，是"时间"和"确定性"。**
- 外贸询盘是**跨天跨周**的长事务（询盘 → 样品 → 报价 → 订单 → 单证 → 收款），
  断点续传、幂等、乐观锁是硬需求，不是加分项；
- 同一个买家**绝不能**被不同版本应答 —— 所以灰度必须**按企业**分流，
  而"按请求随机"在报价场景是事故。

**判断三：能自证的东西才算数，分层不能混。**
公开检索基准（MIRACL / MLDR / Mr. TyDi / mMARCO / MKQA）只能证明"多语种检索管线没问题"，
**证明不了"询盘场景做得好"**——所以评测分两层：公开基准做体检，自建多语种询盘语料做场景层。
厂商给的数字（OKKI / Accio）一律标注"厂商自述口径"，不与自建结果混算。

## 二、这个项目实际做了什么

| 能力 | 落地方式 | 在哪 |
| --- | --- | --- |
| **人在环的确定性** | 11 条闸门 + 闸门令牌（绑定动作、一次性）+ 四类角色可见域 | `runtime/gates.py`、`api/auth.py` |
| **跨天跨周长事务** | 8 状态机 + 断点续传 + 消息幂等 + 乐观锁 | `domain/state_machine.py`、`runtime/supervisor.py` |
| **多语种 RAG** | 三通道 RRF（词法 + 结构化 + 稠密）+ 合规时效过滤 + 术语表 | `retrieval/`、`data/kb_seed.py` |
| **防越权的出稿** | 模型只拿**占位符**，价格/交期/证书号由代码回填；模型写出数字 → 整段丢弃 | `agents/draft_writer.py` |
| **灰度与回滚** | 四类发布单元独立回滚 + 按企业分桶 + 观察窗 + **双索引别名切换** | `release/` |
| **可审计** | append-only 审计哈希链 + 越权尝试也留痕 | `store/base.py` |

## 三、证据（都可复跑，不是自述）

| 证据 | 数字 | 怎么复现 |
| --- | --- | --- |
| 交付门禁 | **十三步全绿** | `dev.ps1 check` |
| 单元测试 | **262 项** | `dev.ps1 test` |
| 自证脚本（双后端） | S1 53 / S2 97 / S3 52 / S4 60 / S5 54 / S6-3 91 | `python scripts/verify_s1.py --backend both` 等 |
| 独立审核脚本（双后端） | S2 106 / S3 90 / S4 85 / S5 54 / S6 64 / S6-3 67 | `dev.ps1 audit` / `audit3` / `audit4` / `audit5` / `audit6` / `audit6r` |
| 代码规模 | 源码 9.7k 行 · 自证与审核脚本 9.7k 行 · 单测 3.0k 行 | — |

**最有说服力的一条**：这个项目的实现不是"写完就交"，而是**被一份先于实现写定的判据反复证伪**。

| 轮次 | 审核发现 | 我改了 |
| --- | --- | --- |
| R22（6 个根因） | 试点企业在放量档被**静默踢出灰度**；任何角色都能建发布；审批人可由请求体自称 | 白名单跨档生效 + 角色闸门 + 审批人只取自会话 |
| R23（5 个根因） | **双索引根本不成立**（块主键是单列 `chunk_id`，同名块互相顶掉）；启动重灌抹掉灰度版；`index_version` 只是装饰字段；灰度到空库版本会让询盘静默退化成空话；证据填"随便写点什么"就能放行 | 主键改复合键 + 两个后端写老库迁移 + 索引版本进检索路径 + 未就绪版本拦下 + 证据必须带编号 |

> 这轮的价值不在"修了 11 个 bug"，在于它证明了两件事：
> **①** 判据先于实现写定，才不会被实现反向塑形；**②** "PRD 说要做"和"真的做到了"之间，隔着一次可复现的对抗。

## 四、差异化：为什么不跟对标产品比功能

对标产品（阿里国际站 AI 生意助手、OKKI、Accio）主打**功能广度与自动化程度**：
多 Agent、多渠道、自动投放、自动跟进。本项目不去比这个。

**本作的定位是"人在环的确定性"**——同样的询盘，为什么草稿能直接给人签、
为什么名字命中一定拦得住、为什么回滚不重建索引、为什么一条询盘从头到尾可追责。
证据形式也不同：对标产品给的是"转化率提升 43.48%"（厂商自述口径），
本项目给的是**可复跑的断言**（谁跑了、哪条红了、改完哪条转绿）。

## 五、诚实的边界（评审时主动讲，反而加分）

**本期做到的是"产品机制可验证的原型"，不是可上线系统。**

- PRD 13.4.12 的 **13 项生产化差距**：无状态多副本、KMS、高可用容灾、SSO、三环境发布、
  备份恢复、50–100 并发压测、真实名单源授权、模型供应商条款、客户数据出境合规、多租户计费……
  **9 项未做、2 项部分做**。
- **三条上线前置条件不在开发范围**：真实名单源商用授权、模型供应商 DPA、客户数据出境告知文本。
  拿不到这三样，项目可以是优秀的产品设计与原型，但**不能真实上线**——这是最大的非技术风险。
- **评测的现实**：公开检索基准只做"体检"，询盘场景靠自建多语种语料；ar 语种按 PRD 降档（缩减版，已显式披露）。
- **公开数字的口径**：OKKI / Accio 的转化率与效率提升全是**厂商自述**，不是第三方统计。

## 六、怎么跑起来（3 分钟）

```powershell
& ".\dev.ps1" up        # 起 PostgreSQL 16 + Redis 7（Docker）
& ".\dev.ps1" serve     # http://127.0.0.1:8080/ui/  ← 前端（真数据模式）
                        # 演示账号：sales / demo1234（另有 manager、compliance、exec）
& ".\dev.ps1" check     # 十三步交付门禁（双后端 + 独立审核）
```

前端支持两种模式：双击 `ui-prototype/index.html` 是 mock 演示（不连后端）；
`/ui/?source=api` 是真数据模式（会话走本地账号密码登录）。

## 七、可能的追问与回答要点

| 追问 | 回答要点 |
| --- | --- |
| 灰度怎么做？为什么按企业不按请求？ | 按请求会让同一买家前后收到不同版本报价；分桶是纯函数（哈希 + 名称规范化），不存分流表，同企业永远同版本 |
| 回滚怎么保证不重建索引？ | 块与向量主键是 `(chunk_id, kb_version)`，两个库版本同名块并存；回滚只改别名指向（这是 R23 抓出来的真 bug） |
| 怎么防止模型乱报价？ | 模型只看到占位符，真值由代码从结构化规格回填；模型输出含数字 → 判越权 → 整段丢弃退回模板 |
| 名单命中怎么保证拦得住？ | 风控**前置**（先风控后应答），命中即阻断、不产生任何对外内容；同时进闸门与审计 |
| 多语种怎么保证不串？ | 术语表 + 跨语种嵌入 + 查询扩展；证书与法规按「买家所在国 + 当前日期」过滤，过期的不许引用 |
| 这个项目最大的不足？ | 生产化那一层基本没做（13 项差距清单）；评测的询盘语料是自建缩减版；没有真实买家流量，门槛 10 顺延 |

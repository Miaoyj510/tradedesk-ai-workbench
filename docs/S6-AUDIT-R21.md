## 二、实现方自证漏掉了什么

这轮最值得记的一条不是缺陷，是**自证的盲区**：

> `verify_s6.py`（24 项）+ `verify_s6_ui.js`（27 项）**全绿**，
> 但 `verify_s6_ui.js` **只跑了 `api.js`（数据层）** ——
> `app.js` 怎么把数据画成界面，**一次都没被跑过**。
>
> 于是"数据对、界面说错"这一类问题**一个都没被发现**：
> 名单条目 ID 写死、mock 固定译文挂在真消息下面、看板顶栏全是 mock 数字、
> 上线门槛卡片写死"已达标"、时间线不转义 —— 12 条渲染层 FAIL 里**大部分**在这一类。

这跟 R19 的教训同型：**评测器与被评测对象共享同一个盲区**。
S5-1c 的"事实保真 100%"只能证明"写阿拉伯数字的编造被抓住了"；
S6 的"前端联调验证全绿"只能证明"**数据层**能拿到数据"。
**"接上真数据"≠"界面显示的是真数据"。**

## 三、违约项（12 个根因）

### R21-01 · 事件流文本与草稿正文**不转义** → 存储型 XSS（P1，安全）

**事实**：`ui-prototype/assets/app.js:320`（审计时间线）与 `app.js:240`（草稿正文）

```js
html += '<li ...><div class="tl-time">' + esc(x.time) + '</div><div class="tl-text">' + x.text + '</div></li>';
...
html += '<div class="draft-body">' + d.body + '</div>';
```

`x.time` 走了 `esc()`，**`x.text` 没走**；`d.body` 也没走。
全文件其余 30 多处动态文本都规规矩矩走了 `esc()` —— **就这两处漏了**。

**可利用性（审核实测）**：`POST /threads/{id}/signoff` 的 `action="transfer"` 允许任意 `reason`，
该 reason 经 `EventType.HUMAN_TAKEOVER` 进事件流 → `_timeline()` 拼成
`"转人工：%s" % reason` → 读模型的 `timeline[].text` → `innerHTML`。

审核方用 `<img src=x onerror="window.__xss=1">` 实测：**载荷原样出现在渲染后的审计时间线里**
（`audit_s6_ui.js` 断言 S6-B3 FAIL）。

**为什么这是 P1**：这是**存储型** XSS —— 载荷写一次，任何打开该线程的人（业务员、经理、合规岗）
都执行一次。本项目里"转交原因"由业务员填写，但 `reason` 字段**无任何服务端校验**，
且同一个 `/signoff` 端点也可被任何持有闸门令牌的调用方写入。
草稿正文 `d.body` 同理 —— 模型出稿或人工修改后的正文直接进 `innerHTML`。

**修法**：两处都走 `esc()`。若草稿正文要保留换行，用 `esc(d.body)` + CSS `white-space:pre-wrap`，
不要用 `<br>` 拼接未转义内容。

### R21-02 · 名单命中面板把条目 ID **写死**成演示条目（P1，对外失真）

**事实**：`app.js:230`

```js
'<p>该买家的最终用户命中出口管制受控条目 <b>CN-2211</b>。按照 GATE-03，...'
```

`CN-2211` 是**写死的字符串**，与后端读模型的证据链无关。

审核实测：真发一条命中 `Demo Metal Trading SARL` 的阿语询盘 →
后端证据链给出的真实条目是 **`CN-2307`**（知识库里有两条名单：`CN-2211` Gulf Trading Partners、
`CN-2307` Demo Metal Trading SARL），而界面上仍显示 **`CN-2211`**。

**为什么这是 P1**：这是**风控界面对外失真**。合规岗看到"命中 CN-2211"，
实际命中的是 CN-2307 —— 两个不同的主体、不同的一致性程序。**界面说的和证据链说的不是一条**，
这在合规场景里是事故级的。

**修法**：条目 ID 一律从 `t.evidence` 取（读模型已经把它结构化给过来了：
`{"k": "条目 ID", "v": "CN-2307"}`），前端不拼、不写死。

它让读的人以为门槛已经过了。

`kpis.avgFirstResponse` / `kpis.costToday`），后端没给的（如引用正确率）
**显示"待评测"而不是写死数字**。

### R21-04 · mock 固定译文挂在**真买家消息**下面（P1，对外失真）

**事实**：`app.js:176-180` —— `msgHTML()` 里写死了三个语种的"中文理解"译文：

const zh = {
  es: '我们是一家巴西经销商。能否为 X-200 提供 5000 台 FOB 深圳的报价？...',

### R21-05 · 成本看板的"单位成本"是**每条询盘**还是**每次调用**？（P1，口径）

**事实**：读模型 `_cost_series()`（`workbench.py:350-357`）

```python
by_lang.append({"lang": lang, "n": n,
                 "y": round(float(b.get("cost_cny") or 0.0) / n, 6)})
```

`n` 是 `llm_usage` 的**调用行数**（`summarize_llm_usage` 里 `bucket["count"] += 1` 计的是行），
`y = 总成本 / 调用次数` → **元 / 次模型调用**。

而界面上写的是：
- `app.js:469` —— 折线图角标 `单位：元 / 条询盘`
- `dashboard.html:91` —— `成本 = Σ(tokens_in×单价_in + tokens_out×单价_out) ÷ 询盘条数`

审核实测：造一条询盘的 3 次调用（对话 0.015 元 + 嵌入 0.005 元 + 一条单价未核实的行），
**这条询盘共 0.02 元**；读模型给 `y = 0.006667`（= 0.02 ÷ 3 次调用）。
**按"元 / 条询盘"应是 0.02。**

**为什么这是 P1**：PRD 12.4 的硬指标是 **"单位询盘 Token 成本 ≤ 0.2 元/条"** ——
分母是**询盘条数**。现在看板标"元/条询盘"、算的是"元/次调用"，
**分母错了就等于把硬指标报错了**（一条询盘 3~4 次调用 → 数字被摊薄到 1/3~1/4）。
这跟 R19-02 是同一族错误：**口径声明比实际乐观**。

**顺带**：`costTrend` 用的是同一个 `_cost_series` 口径，趋势折线同样偏。

**修法**：`llm_usage_summary` 的 `by_lang`/`by_day` 需要**同时给"调用数"与"询盘条数"**
（询盘数 = `count(distinct thread_id)`），看板的"单位成本"用**询盘条数**做分母，
调用数单独一列（"调用次数"）。

### R21-06 · `kpis.draftReady` 把**名单阻断/已发送**的线程算成"草稿就绪"（P2，口径）

**事实**：`workbench.py:344`

```python
"draftReady": len(threads) - pending,
```

`pending` = 带 `awaiting_signoff` 标志的线程数。所以 `draftReady` = 线程总数 − 待签核数，
把**名单命中的阻断线程**（FR-EVA-07：**不生成任何回复**）与**已发送的线程**都算成了"草稿就绪"。

审核实测：7 条线程、4 条待签核 → `draftReady = 3`；**实际有草稿正文的是 6 条**。
两个数都对不上：口径既不等于"有草稿的线程数"，也不等于 mock 的 `78`（那是"草稿可用率 %"）。
前端 `app.js` 没用这个字段（`dashboard.html` 的"草稿可用率"是写死的 78%），
但读模型对外给出的是一个**含义不明的数字**。

**修法**：`draftReady` = **有草稿正文**的线程数（与 §S6-D 断言一致）；
若还要"草稿可用率 %"，另给一个字段并说明分母（分母是什么？全部线程还是已生成草稿的线程）。

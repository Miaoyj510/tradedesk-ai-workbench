## 二、为什么 4b 的"稠密通道"目前**不是召回通道**

这一条不是缺陷，是**口径必须说清的事实**，否则 4c 基线里的结论会被读错。

RRF 的贡献是 `1/(k + rank)`：

| 通道 | k | 第 1 名贡献 | 该通道最差一名（截断处）贡献 |
| --- | --- | --- | --- |
| 结构化 | 10 | 0.0909 | 0.0909（只有一条） |
| 词法 | 60 | 0.0164 | 1/(60+15) = **0.0133**（评测 top_k=5）｜1/(60+24) = 0.0119（Agent top_k=8） |
| 稠密 | 100 | **0.0099** | 0.0099 |

词法通道被截断在 `max(top_k×3, 10)` 条，于是**只要词法有任何一条命中，
稠密单独发现的块（贡献 ≤ 0.0099）永远排在所有词法命中之后** → 进不了 top-K。

实测（审核方探针，哈希假嵌入器 + 真实知识库）：

```
有词法命中时，出现"纯稠密块"的查询数：0 / 9
词法完全落空时（"xyzzy qwerty nonsense"）：5 条纯稠密命中进入结果
```

所以稠密通道当前的真实角色是 **① 词法落空时的兜底 + ② 给已有词法命中加 ≤0.0099 的弱加权**，
**不是**"把词法找不到的东西召回来"。文档里"稠密通道是召回辅助"的说法偏乐观，
建议改成"兜底 + 弱加权"，并说明它当前**不具备独立召回能力**（否则 top_k 调大到 14 以上才会改变）。

## 三、违约项（13 个根因）

### R17-01 · PostgreSQL 近邻检索**不按库版本过滤** → 旧版本向量挤空稠密通道（P1，双后端不一致）

| | |
| --- | --- |
| 条款 | 验收 4a-03「按库版本隔离」、4b-07「PostgreSQL 侧近邻检索」；PRD 13.4 选型轴③ |
| 位置 | `src/tradedesk/store/postgres_store.py::search_kb_vectors` |

```sql
SELECT chunk_id, 1 - (embedding <=> CAST(%s AS vector)) AS score
FROM kb_embeddings WHERE embedding IS NOT NULL
ORDER BY embedding <=> CAST(%s AS vector) LIMIT %s
```

**没有 `kb_version` 条件**。而内存口径（`list_kb_embeddings(kb_version)`）是过滤的 ——
于是同一个检索在两个后端上是两回事。实测：

```
写入 kb-A（当前版本）1 条 + kb-B（旧版本）1 条，同一个查询向量：
  内存口径（list_kb_embeddings("kb-A")） → 只有 kb-A 那条
  PG 近邻检索（search_kb_vectors）      → kb-A 与 kb-B 都返回
```

**后果比"多返回几条"更严重**：`LIMIT` 在版本过滤**之前**生效，旧版本的向量会把名额占满。
把 12 条旧版本向量设成与查询向量完全一致（换库版本后旧向量留在库里正是这种情形）后：

```
PG 稠密通道返回 0 条 —— 当前库的向量被挤出 LIMIT，
命中块在块表里又找不到（chunk_id 不在当前版本）→ 全被丢掉
同一场景在 SQLite（走内存索引，按版本过滤）上返回 10 条
```

**稠密通道在 PostgreSQL 上静默变空，在 SQLite 上正常** —— 这正是 S3 反复强调的
"双后端必须逐条一致"被破坏。修法：SQL 加 `AND kb_version = %s`（并把版本参数传进来）。

### R17-02 · HNSW 索引**只在建表时创建**，存量库永远没有 ANN 索引（P1，4b-07 声明不成立）

| | |
| --- | --- |
| 条款 | 验收 **4b-07**「PostgreSQL 侧近邻检索走 **pgvector + HNSW**（生产形态）」；R15 记账项 N7 |
| 位置 | `src/tradedesk/store/postgres_store.py::_init_embedding_table` |

`CREATE INDEX IF NOT EXISTS idx_kb_embeddings_hnsw ... USING hnsw` 写在
**"表不存在"的分支里**（`if not exists:` → 建表 → 建索引 → `return`）。
存量库走的是"表已存在"分支：改列维度 → 加 `content_fp` 列 → **`return`，从不建索引**。

实测（本机三个库都是 4a 时代建的）：

```
tradedesk_a      → kb_embeddings_pkey
tradedesk_b      → （连表都没有）
tradedesk_audit_b→ kb_embeddings_pkey
新建库（走建表分支）→ kb_embeddings_pkey + idx_kb_embeddings_hnsw   ← 只有新建库有
```

于是**所有从 4a 升上来的部署，`ORDER BY embedding <=>` 都是全表线性扫描** ——
而 4b 正是为了 50–100 并发下的检索瓶颈才接 pgvector 的（R15 的 N7）。
另外 `CREATE INDEX` 被 `except: pass` 吞掉，**建失败也没有任何日志**。

修法：把建索引挪到"表已存在"分支里也执行一次（或独立成一步）；失败要打日志而不是静默。

### R17-03 · 进程内的向量索引是**启动时的快照**，重建索引后稠密通道不失效（P2，R11-07/R15-01 同型）

| | |
| --- | --- |
| 条款 | 验收 4a-04 幂等与失效键；S3 的 R11-07（改库后同进程不生效）在向量层的翻版 |
| 位置 | `src/tradedesk/retrieval/store_retriever.py::StoreRetriever.__init__ / dense_hits` |

`vector_index` 是构造时传入的**一次性快照**，`dense_hits` 直接用它，从不重载。
块内容走内容指纹失效（R15-01 修对了），**向量本身不走**。

实测（换嵌入器全量重建索引后，同一个检索器）：

```
陈旧快照前 2 条 = [('KB-R-AE099', 0.3569), ('KB-S-CN2307', 0.1836)]
库里现向量前 2 条 = [('KB-T-LEADTIME', 0.2661), ('KB-S-CN2211', 0.1181)]
```

**库里已经是新向量，检索用的还是旧向量**。生产里就是：发布流水线重建索引 → 应用不重启 →
稠密通道返回旧内容（且不会报错）。

修法：`StoreRetriever` 按"存储层向量指纹"失效（与块内容指纹同一套做法），或每次稠密检索前
比对向量条数/模型标签。

### R17-04 · `NullEmbedder` 对多条文本返回**同一条**向量（P2，R16 重写引入）

| | |
| --- | --- |
| 条款 | 验收 4a-05「余弦 TopK：排序正确」；R15-05 的修复不得引入新问题 |
| 位置 | `src/tradedesk/retrieval/embedders.py::NullEmbedder.embed` |

R16 把占位嵌入器改成"固定 256 维 + 归一"，但把 `vec` 提到了**循环外**，
每条文本都在**同一个累加器**上累加，最后把**同一条向量**返回给所有文本：

```python
vec = [0.0] * self.dim          # ← 循环外
for t in texts:
    for g in char_ngrams(t):
        vec[idx] += sign        # ← 每条文本都往同一个累加器里加
    out.append(_normalize(vec)) # ← 每条文本返回的是"整批累加"的同一条向量
```

实测：`NullEmbedder().embed(["手动搬运车", "电动搬运车"])[0] == [1]` → **True**。
用它建的索引里所有块的向量都相同 → 余弦恒为 1 → **向量通道无从排序**。
（R15-05 修的是"维度随批次变、不归一"，这个新问题是"多文本同向量"。）

修法：`vec` 移进循环（与 `HashEmbedder` 一致）。

### R17-05 · 评测的 **Macro-F1 把无样本的 `unknown` 标签算进分母** → 与 PRD 12.3 不可比（P1，口径）

| | |
| --- | --- |
| 条款 | PRD 12.3「意图 Macro-F1 ≥ 0.90（en/es）、≥ 0.85（ar）」——是**五类意图**的宏平均 |
| 位置 | `scripts/eval_retrieval.py::macro_f1` |

```python
labels = INTENTS + ["unknown"]   # ← 语料里没有任何 unknown 样本，它的 F1 恒为 0
total / len(labels)               # ← 分母 6，不是 5
```

没有样本的标签，F1 必然是 0，却仍然占着宏平均的分母 → **四个语种的 Macro-F1 被系统性压低 1/6**。
审核方按 PRD 五类口径复算：

| 语种 | 脚本报的 | PRD 五类口径 | 差 |
| --- | --- | --- | --- |
| en | 0.6799 | **0.8158** | -0.1359 |
| es | 0.5847 | **0.7016** | -0.1169 |
| ar | 0.6338 | **0.7605** | -0.1267 |
| zh | 0.6088 | **0.7306** | -0.1218 |

**方向不变**（离门槛仍远），但**报出去的数字与门槛不可比**：基线文档第五节拿
"en 0.68 / es 0.58 / ar 0.63"直接对 PRD 的 0.90 / 0.90 / 0.85 说"远不达门槛"，
用的却是一个被自己口径压低了的数。这是 S3 在"库版本号两份"上栽过的同一个坑的变体：
**数字口径失真要当缺陷，不当笔误**。

修法：只对**语料里实际出现的标签**求宏平均（或把 unknown 的样本补齐），并同步改基线表。

### R17-06 · 评测报表无法区分"稠密通道**失败**"与"稠密通道**召回差**"（P1，口径）

| | |
| --- | --- |
| 条款 | PRD 9.5 两层口径；R15-04 的教训（"有块但没有向量"不能静默） |
| 位置 | `scripts/eval_retrieval.py::main / evaluate` |

查询嵌入失败（key 失效 / 网络不通 / 维度不对）会**逐条降级**，`retriever.dense_skipped`
里有记录 —— 但**评测脚本从不读它**。后果：

```
稠密通道指标 → 全是 0.000
报表头部     → 「稠密通道：**启用**（向量索引 N 条）」
基线结论 2   → 「稠密通道在阿语上几乎无效」
```

读者会把"**通道根本没跑**"读成"**模型在阿语上不行**"。这与 R15-04 完全同型：
一次失败被写成了"能力不足"。R15-04 当时改了启动日志，这次**同一个坑在评测侧又踩了一遍**。

修法：报表必须打印 `dense_skipped` / 稠密通道实际命中条数；稠密通道一条都没命中时，
指标列必须显式标注"**通道未生效**"，不得以 0.000 的形式混进能力表。

### R17-07 · 评测不报稠密通道的调用次数与成本口径（P2，成本）

| | |
| --- | --- |
| 条款 | PRD 12.5 门槛 4「单位询盘 Token 成本 ≤ 0.2 元/条」；S4-ACCEPTANCE 第七节 4b-05 |
| 位置 | `scripts/eval_retrieval.py` |

评测跑的是**每条语料 1 次云端查询嵌入**（160 条语料 = 160 次调用），脚本里既没有

修法：报表加一行"稠密通道：调用 N 次 / 估算 ¥X"，并支持 `--no-dense` 显式关闭。

### R17-11 · 成本计量漏掉**重试**（P2，`≤0.2 元/条` 的基线会低估）

| | |
| --- | --- |
| 条款 | PRD 12.5 门槛 4；S4-ACCEPTANCE 4b-05「每条询盘只触发 1 次云端嵌入调用」 |
| 位置 | `src/tradedesk/retrieval/store_retriever.py::dense_calls` vs `embedders.py::RemoteEmbedder.calls` |

`dense_calls` 数的是 **`embed_query` 次数**，不是**实际云端调用次数**。
网络故障时 `RemoteEmbedder` 会重试（默认 2 次）：

```
网络抖动 2 次后成功：dense_calls = 1，实际 HTTP 调用 = 3
```

重试是**要花钱的**。S5 拿 `dense_calls` 当成本基线 → **最坏低估到 1/3**。
验收 4b-05 的措辞（"只触发 1 次云端嵌入调用"）在有重试时不成立。

修法：成本口径改用 `RemoteEmbedder.calls`（HTTP 次数），或在文档里写明"每条询盘
1 次嵌入请求、最多 3 次 HTTP 调用"。

### R17-12 · 稠密通道当前**不具备独立召回能力**，文档口径偏乐观（P2）

见第二节的推导与实测。验收 4b-01「稠密通道权重最低（k=100）」本身没错，
但它带来一个未写下的后果：**稠密单独命中的块在 top_k ≤ 13 时永远进不了融合结果**
